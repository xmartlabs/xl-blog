# XL Blog

The Xmartlabs blog (https://blog.xmartlabs.com): a [Next.js 16](https://nextjs.org) site with [Payload CMS 3](https://payloadcms.com) built in, a Postgres database, and hosting on Vercel.

- Public site: `/`, `/page/<n>/`, `/categories/[<slug>/[page/<n>/]]`, `/blog/<slug>/`, `/authors/<slug>/`, `/tags/[<tag>/]`, `/sitemap-index.xml`.
- Admin panel (the CMS): `/admin`. Bloggers sign in with their @xmartlabs.com Google account.

## Where things live

| `src/blocks/`                  | Post body blocks: video, image/gallery, table, code, HTML embed.                                                                 |
| `src/components/rich-text/`    | Lexical → HTML renderer for post bodies (keeps the exact markup of the old site).                                                |
| `src/components/`              | React components of the site (nav menu, cards, post page, …).                                                                    |
| `src/components/admin/`        | Admin panel branding: logo, nav icon, dashboard welcome panel. Styles: `src/app/(payload)/custom.scss`.                          |
| `src/lib/`                     | Data access (`posts.ts`, Payload Local API), SEO helpers, sitemap, revalidation hooks, `safeInternalPath` (`redirects.ts`).      |
| `src/auth/`                    | Google sign-in (`payload-oauth2`), domain check, password-login switch, break-glass admin seed.                                  |
| `src/migrations/`              | Database migrations (run on every Vercel build).                                                                                 |
| `public/`                      | Static files served at the site root. `public/images/…` holds every image of the old posts (`/images/foo.png`).                  |
| `scripts/migrate-content.ts`   | One-off import of the old Markdown blog into Payload (see "Content migration").                                                  |
| `migration/legacy/`            | Snapshot of the old site's rendered post bodies + metadata, the input of the import; also used for the old Jekyll URL redirects. |

## Local development

Requirements: Node 24.22.3+ (`.nvmrc`), Docker.

```sh
nvm use                      # Node 24.22.3
npm install
cp .env.example .env         # then fill in PAYLOAD_SECRET (openssl rand -hex 32) and DATABASE_URL
npm run db:up                # Postgres 17 in Docker (docker-compose.yml)
npm run dev                  # http://localhost:3000, admin at http://localhost:3000/admin
```

In development the database schema is pushed automatically from the Payload config (no migrations needed). To get the real content locally, run the content migration (below).

**Integration tests** (`npm run test:int`, `tests/int/`) run the real Payload config against a separate database, `xlblog_test` on the same server (`TEST_DATABASE_URL` overrides it; its name must end in `_test`). The global setup drops, recreates and migrates it on every run (`payload migrate`, schema push off, like a deploy), so it never touches your `xlblog` data and can be left in place. Every assertion runs with `overrideAccess: false` and an explicit `user`, like the REST API does.

**End-to-end tests** (`npm run test:e2e`, `tests/e2e/`, Playwright + Chromium) run a production build: run `npm run build` first (with the database up), and `npx playwright install chromium` once. The web server command recreates its own database, `xlblog_e2e` on the same server (`E2E_DATABASE_URL` overrides it; the name must end in `_e2e`), applies the migrations, seeds 1 author, 2 categories, 3 posts plus 2 imported legacy posts (embeds; code and images) and a test editor and admin (random passwords per run, kept in the git-ignored `tests/e2e/.cache/`), then runs `next start` on port 3003 (`E2E_PORT`) with a test `CRON_SECRET` and a fake Google OAuth client. The tests sign in through `POST /api/users/login` and cover publishing/unpublishing and revalidation, draft privacy (preview route, stale draft-mode cookie, REST API), the admin's Preview button and Live Preview, the Google sign-in redirect/cookies and forged callbacks, role and secret checks, the server-rendered 404 page, robots.txt, the CSP header and its report endpoint (no CSP violations on the home, a post with embeds and the admin post editor), the login cookie's attributes, and accessibility regressions (axe, against a baseline). Google itself is never called: domain rejection (personal Gmail, wrong `hd`, unverified email) is covered by the unit tests with a mocked Google (`tests/google-*.test.ts`). The e2e server regenerates pages into the build's cache (`.next`) from the e2e database, so rebuild before using that build for anything else. `npm run test:parity` (`tests/parity/`) compares the site with the live blog and isn't part of CI.

## Users and roles

- **Editors** (everyone by default): any @xmartlabs.com Google account gets an `editor` user on first sign-in. Editors can create, edit, publish and schedule posts, and add authors.
- **Admins**: everything editors can do, plus deleting posts/authors, managing categories, and promoting/demoting users (Users → open the user → Roles).
- **First admin**: Google sign-in always creates editors, so nobody can make themselves admin by logging in. The first admin comes from `FIRST_ADMIN_EMAIL` instead: on startup, **only while the users table is empty**, that user is created as admin (`src/auth/seedFirstAdmin.ts`). With password login on (default) it also needs `FIRST_ADMIN_PASSWORD`; with `DISABLE_PASSWORD_LOGIN=true` it's created without a password and that person becomes admin by signing in with Google as that address (sign-in matches users by email). Once any user exists, the variables do nothing. See "First admin in production" below.
- **Password resets** ("Forgot password?" on the login page) only send an email when `RESEND_API_KEY` and `EMAIL_FROM` are set; otherwise the reset link is only written to the server log, and an admin resets the password from Users instead.
- **Password login** is locked for 10 minutes after 5 wrong passwords. Once the real admins have signed in with Google, set `DISABLE_PASSWORD_LOGIN=true` in production: the login page then only shows the Google button and `/api/users/login` is refused. The break-glass account stays in the database (and works again if the variable is removed and the site redeployed). With password login off, a first admin seeded into an empty database gets no password: that person becomes admin by signing in with Google as `FIRST_ADMIN_EMAIL`. Note that payload-oauth2 only uses Payload's server-side sessions while the local strategy is on, so with password login off, signing out clears the cookie but can't revoke the token. To limit that, tokens then last 8 hours instead of 7 days (editors sign in with Google again after that); deleting the user still locks it out immediately.

### First admin in production

1. Before the first deploy, set `FIRST_ADMIN_EMAIL` to the real address of the person who will administer the blog (e.g. your own `@xmartlabs.com` email) and `FIRST_ADMIN_PASSWORD` to a strong password (keep it in the team vault as the fallback).
2. Deploy. On the first start against the empty database, that user is created as **admin**.
3. That person signs in with **Google** using the same address and lands in the same admin account (Google sign-in matches users by email).
4. They promote the other admins in **Users → open the user → Roles → admin** (everyone else signs in with Google and starts as editor).
5. Turn on Google-only login: set `DISABLE_PASSWORD_LOGIN=true` and remove `FIRST_ADMIN_PASSWORD` from the Vercel environment, then redeploy. The fallback admin stays in the database; removing `DISABLE_PASSWORD_LOGIN` and redeploying brings password login back if Google sign-in ever breaks.

Locally the same applies to your own database: the user from `FIRST_ADMIN_EMAIL` is created on the first `npm run dev` against an empty database.

### Google sign-in setup (Google Cloud console)

1. Use a project of the xmartlabs.com Google Workspace organization.
2. **OAuth consent screen**: user type **Internal** (only accounts of the organization can sign in), app name "XL Blog", scopes `openid`, `email`, `profile`. Check the project's organization in **IAM & Admin → Settings**: a project created under another organization fails with `Error 403: org_internal` for Xmartlabs accounts.
3. **Credentials → Create credentials → OAuth client ID**, type "Web application". Authorized redirect URIs:
   - `http://localhost:3000/api/users/oauth/google/callback`
   - `https://blog.xmartlabs.com/api/users/oauth/google/callback`
   - optionally one fixed preview host, e.g. `https://<branch alias>.vercel.app/api/users/oauth/google/callback`
4. Put the client id and secret in `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (locally in `.env`, on Vercel in the project's environment variables).

The sign-in flow uses a `state` cookie (CSRF) and PKCE (S256), both short-lived HttpOnly cookies scoped to `/api/users/oauth/google`, and returns to the page the user was trying to open (Payload's `?redirect=`, sanitized to a same-site path; default `/admin`).

Google only redirects to registered URIs, so Google sign-in works on production, localhost and the registered preview host, **not on random per-deployment preview URLs**. On preview deployments `NEXT_PUBLIC_SERVER_URL` falls back to the branch URL (`VERCEL_BRANCH_URL`), which is stable per branch; register the one you use, or set `NEXT_PUBLIC_SERVER_URL` for the Preview environment to that host.

## Writing posts (bloggers)

1. Open https://blog.xmartlabs.com/admin and click **Sign in with your Xmartlabs Google account**. The dashboard shows these steps too.
2. **Posts → Create new** (or **New post** on the dashboard). Fill in the title (12+ characters), category, author (preselected when your user is linked to an author), 1–5 tags, a 16:9 thumbnail (at least 1600×900; set its focal point), and the body. The slug (URL `/blog/<slug>/`) is filled from the title; change it before publishing if needed.
3. Body: rich text plus blocks (`+` or `/` menu): **Images (one or a row)**, **YouTube or video file** (any YouTube link — watch, youtu.be, shorts, embed — or the video id; or an uploaded MP4/WebM), **Table**, **Code**, **Raw HTML (advanced)** (mostly imported content; e.g. tweets or iframes; scripts in it are loaded once per page).
4. **Preview**: drafts autosave. The **Live Preview** tab shows the post next to the editor and updates as you type; **Preview** opens it in a new tab. Only signed-in users see drafts.
5. **Publish** makes it live within seconds (the affected pages are regenerated). **Unpublish** takes it down.
6. **Schedule**: next to Publish, choose **Schedule Publish** and pick a date/time. A cron job publishes due posts every 5 minutes.

Authors without an account are plain `authors` entries (name, slug, picture, profile URL); a user doesn't need to be an author and vice versa.

**Linking a user to their author** (admins): Users → open the user → **Author** (sidebar). New posts that user creates then preselect that author. It is never linked automatically on Google sign-in, even when an author with the same name exists (names aren't unique and a wrong link would misattribute posts), so link new bloggers by hand after their first sign-in. Editors can't change their own link.

**Images**: new uploads get a `card` size (800×450, cropped around the focal point) for post cards and a `hero` size (1600 px wide) for the post page and its social image; images smaller than a size, videos and legacy URL-based images use the original file.

## Database migrations

Development uses schema push; production runs migrations on every deploy (`npm run ci` = `payload migrate && next build`).

When you change collections, fields or blocks:

```sh
npm run payload migrate:create <short-name>   # with the local DB up; writes src/migrations/<date>_<name>.ts
npm run generate:types                        # updates src/payload-types.ts
```

Review and commit the migration with the code. The next Vercel build applies it to the Neon database before building.

## Content migration (one-off)

```sh
npm run seed:migrate-content                                   # categories, authors, all 175 posts
MIGRATE_ONLY=vytallink-app,a-look-back-at-2020 npm run seed:migrate-content
npx payload run scripts/compare-bodies.ts                      # DB render vs migration/legacy/bodies: expect 175/175 exact
```

The import is idempotent (upsert by slug) and publishes posts with their original dates. It reads `migration/legacy/posts.json` and `migration/legacy/bodies/<slug>.html` (the verified rendering of the old site) and `content/{authors,categories}/*.yml`. To run it against production, point `DATABASE_URL` at the production database (after `payload migrate`) and set `REVALIDATE_URL` (the site's origin) and `CRON_SECRET`: at the end the script calls `POST <site>/next/revalidate/` so pages pre-rendered while the database was empty (home, tags, sitemap) are regenerated. That endpoint also works on its own, for `Authorization: Bearer $CRON_SECRET` or a signed-in admin.

## Deploy (Vercel)

`vercel.json` sets the framework, the build command `npm run ci`, and the scheduled-publishing cron (`/api/payload-jobs/run/` every 5 minutes; Vercel sends `Authorization: Bearer $CRON_SECRET`). Pages are statically generated at build time from the database and regenerated on demand when content changes (`src/lib/revalidate.ts`). See `MIGRATION-TODO.md` for the setup checklist.

## Security headers, robots.txt

- **Login cookie**: Payload's `payload-token` cookie (password login and Google sign-in) is `HttpOnly`, `SameSite=Lax`, and `Secure` whenever the site URL (`NEXT_PUBLIC_SERVER_URL`, else the Vercel URL) is https (`src/auth/cookies.ts`). On http://localhost it isn't Secure, so local dev and the tests work.
- **robots.txt** (`src/app/robots.ts`, rules in `src/lib/robots.mjs`): production (`VERCEL_ENV=production`, or outside Vercel at https://blog.xmartlabs.com) and localhost allow everything except `/admin`, `/api` and `/next/`, and list `Sitemap: https://blog.xmartlabs.com/sitemap-index.xml`. Vercel preview deployments (and production builds on an unknown host) get `Disallow: /` plus an `X-Robots-Tag: noindex, nofollow` header on every response (`next.config.mjs`). Both are decided at build time.
- **Content Security Policy** (`src/lib/csp.mjs`, sent by `next.config.mjs`): **report-only** for now. The public site's policy allows the site itself, the embeds in posts (YouTube, Twitter/X widgets, Instagram), GTM/Google Analytics when `NEXT_PUBLIC_GTM_ID` is set, the host of `NEXT_PUBLIC_FORM_URL` (Typeform iframe), the Vercel Blob store (videos) and `https:` images (legacy posts show images from many hosts). The admin panel (`/admin`) has its own, more permissive policy (Monaco editor from jsDelivr, blob: workers, Vercel Blob client uploads) and `frame-ancestors 'none'`. Violations are reported to `POST /next/csp-report/` (`report-uri` for Firefox/Safari, `report-to` + `Reporting-Endpoints` for Chrome), which logs one `[csp] …` line per violation (query strings stripped) and stores nothing; search the Vercel logs for `[csp]`. Chrome only sends `report-to` reports to https endpoints, so locally use the page's `securitypolicyviolation` events (as the e2e test does) or the DevTools console.
  - `script-src` needs `'unsafe-inline'`: Next writes each statically generated page's React Server Components payload as inline `<script>` tags whose content changes per page and build, so hashes can't list them, and a nonce would need every page rendered per request (no static pages). `style-src` needs it for the `style` attributes in legacy post bodies.
  - **Switching to enforcing**: after a period of clean `[csp]` logs in production (GTM can load other tags configured in the container; add their hosts to `publicDirectives`), set `CSP_ENFORCE=true` in Vercel and redeploy. Check the site, the embeds, the "Let's talk" form and the admin (Live Preview, code fields, uploads) on a preview deployment first.
  - Tuned to zero violations by visiting every sitemap URL (722), two 404s and `/admin/login/` on a production build of the full content, plus the admin post editor in the e2e tests (`tests/e2e/security.spec.ts`). Not exercised locally: GTM/GA with a real container and the Typeform iframe (both env vars were empty).
- **Accessibility**: `tests/e2e/a11y.spec.ts` runs axe on the home, a category, a post, the 404 and `/admin/login/`, and fails only on regressions against `tests/e2e/a11y-baseline.json` (the legacy design's current issues; see `tests/e2e/A11Y-FINDINGS.md`). After fixing issues, refresh the baseline with `A11Y_UPDATE_BASELINE=1 npm run test:e2e -- a11y.spec.ts`.

## Rendering notes

- Post bodies are rendered from Lexical to one HTML string inside `.bodyPostContainer` (`src/components/rich-text/to-html.ts`), so the CSS that targets direct children (`.bodyPostContainer > p`, `> img`, …) matches the old markup exactly.
- SEO tags (`<title>`, combined `name`/`property` meta, canonical, Twitter card) are rendered by `src/components/seo/Seo.tsx` in each page and hoisted into `<head>` by React.
- Old Jekyll URLs (`/YYYY/MM/DD/<file name>/`) redirect to `/blog/<slug>/` (`next.config.mjs`, generated by `src/lib/legacy-redirects.mjs`, plus a short explicit list for old links the file names don't produce).
- Unknown posts, categories, tags, authors and page numbers return a 404 with the styled 404 page in the HTML: pages return `<NotFoundPage />` (`src/components/not-found/NotFoundPage.tsx`) instead of calling `notFound()`, which in Next 16 would send an empty error shell and render the page on the client.
